# 寻枢（Xunshu）后期改造计划

v1.0 · 2026-11-08 · 依据：0.17.0 源码审读、合成基准、公开资料调研

## 0. 一页结论

**判断**：寻枢的功能广度（Everything 式查询语法、EFU、属性、正文、OCR、语义、双 Ctrl 快搜）已经不少。离“最好用”的差距集中在三处，而且都不是继续堆功能能解决的：

1. **首次体验与范围控制**。源码里其实有首次向导，但触发条件和关闭逻辑让多数用户看不到、关掉后找不回；安装器本身没有任何范围选择；向导里选的范围，和“极速通道”实际索引的范围也不是同一套。这就是“装完不能选盘、选类型”的根因（见 §3.1）。
2. **引擎的结构性上限**。两套索引并存（SQLite 全表扫描 + 内存字节带），都是线性扫描；默认安装免提权，所以默认走目录枚举，文档实测约 450–1430 项/秒，而 MFT 路径约 28.9 万条/秒。Python + PyQt5 的常驻体积，也决定了“内存比 Everything 更少”很难做到（§3.2）。
3. **治理与合规**。文档互相矛盾（路线图写“P0–P7 全部已完成”，验证文档写“尚未验收”）；部分模块的依据是对商业软件的恢复或探测，且文档自己承认没有取得许可；PyQt5 的 GPL 与 MIT 声明并存。要做“市面最好”并公开发布，这是必须先清的雷（§9）。

**建议路线**（详见 §7）：

- 阶段 0（第 1–2 周）基线与治理。
- 阶段 1（第 2–5 周）体验止血：只改现有代码，用户立刻能感知。
- 阶段 2（第 5–14 周）新核心 `xs-core`（Rust，常驻、省内存、毫秒级）。
- 阶段 3（并行）检索质量与 Listary 式系统集成。
- 阶段 4 内容、语义与 Agent。阶段 5 发布打磨。

保留的资产：查询语法的语义规格、测试用例、内容抽取思路、双 Ctrl 交互、“诚实进度”原则。会被替换的：索引与查询执行、常驻进程，最终包括 UI 外壳。

需要你拍板的事见 §10。其中“是否公开或商业发布”决定 §9 的力度，“是否接受一次管理员授权”决定能否做到全盘秒级就绪。

## 1. 我做了什么，没做什么

**做了**：通读 341 个文件（约 4 万行 Python，加文档与脚本），重点读了 ROADMAP、VALIDATION、SCAN\_SETUP、RESEARCH\_ALGORITHMS，`gui.py` 启动流程，`scan_setup_ui.py`、`auto_index*.py`、`index.py`、`fast_service.py`、`live_index.py`、`compact_index.py`、`search_backend.py`，以及安装脚本 `xunshu.iss`。在 Linux 沙箱里跑了部分单测和一个合成基准，并检索了 Everything、Listary、Gety、plocate、nucleo、Model2Vec、ntfs-reader 的公开资料。

## 2. 第一性原理：这类软件到底在解决什么

用户要的是：\*\*从“我想要那个文件”到“它被打开”，耗时最短、脑力最少，且结果可信。\*\*拆开看：

总耗时 = 唤起 + 输入 + 等结果 + 辨认 + 执行；前提是**覆盖**（想找的在索引里）和**新鲜**（刚改的也在）。

由此推出四条硬约束，后面所有取舍都回到它们：

1. **覆盖**：找不到比慢更致命。默认范围必须让绝大多数人装完就能搜到常用东西。
2. **延迟**：从输入到出结果要低于人的感知阈值（目标 P95 ≤ 16 ms，一帧）。超过它，体验从“思维延伸”变成“等待”。
3. **资源**：常驻软件的成本按“全天开机”计，内存、CPU、磁盘 IO 都要让用户无感。
4. **信任**：本地、可审计、不乱动文件、默认不联网（你们已有的原则），给 AI 的上下文必须可控。

三款老牌软件在这四条上押的注不同：

|  | Everything | Listary | Gety |
| --- | --- | --- | --- |
| 主要押注 | 覆盖、延迟、资源 | 唤起、执行、辨认 | 内容覆盖、AI 上下文 |
| 做法（公开资料） | 默认索引所有固定 NTFS 卷；NTFS 直读主文件表并靠变更日志保持新鲜；数据库常驻内存，退出时才落盘 | 文件对话框 Quick Switch、Ctrl-Ctrl 唤起、模糊匹配与学习排序、全拼与模糊拼音、动作与命令；7 版与 Gety 联动 | 本地优先；关键词加语义检索、OCR、连接器；通过 MCP、API、CLI 向 Agent 提供片段，可逐次授权 |
| 短板（我的归纳，非官方说法） | 排序弱，功能靠自学；官方稳定版以文件名路径为主，内容索引属新版可选能力，立项前以官网为准 | 功能发现性差、高级能力需付费（多篇评测提到）；文件名之外的内容检索交给 Gety | 文件名秒搜不是主打，由 Listary 补位 |

所以“集三家之长”不是功能清单叠加，而是：**Everything 的底座（覆盖、延迟、资源）+ Listary 的入口与排序（唤起、执行、辨认）+ Gety 的内容与 Agent 层（做成可选、按需、低功耗）**。真正的创新落在三层之间的缝隙里：同一个搜索框统一三路召回、统一排序、统一解释“为什么命中”，而且用同一份范围设置管住全部三层。

## 3. 现状诊断（以源码为证）

### 3.1 首次引导与范围选择

**源码里已经有向导，但它大概率没有出现在你的使用路径上。**

1. **触发条件苛刻。** `gui.py` 启动时，只有“没有标记完成，且索引里一个根目录都没有”（或命令行带 `--setup-wizard`）才弹向导。升级安装、旧库、早期版本自动登记过 `C:\` 的用户一律看不到。
2. **关掉就永久消失。** `auto_index_ui.py` 的 `finished` 回调不论用户点“开始扫描”还是“稍后设置”，都把 `setup_wizard_completed` 设为 True。点过一次“稍后设置”（或直接关窗）后，不会再主动提示。
3. **安装器没有任何范围页。** `xunshu.iss` 是免提权、仅当前用户安装，只有安装路径和桌面图标选项；没有“极速模式（需管理员）”选项，也没有范围或类型页。
4. **一页塞满。** 向导是一个 760×560 的窗口，同时放磁盘与目录清单、5 个批量或发现按钮、6 类文件类型、自定义后缀、正文开关、OCR 开关和说明。没有推荐预设，没有每个磁盘的容量、文件系统、预估文件数、预估耗时，用户无从判断“该勾什么”。
5. **范围和极速通道脱节。** `windows_support/runtime.py` 的 `--internal-fast-service` 固定对 `SystemDrive` 建 MFT 快索引，不读用户选的卷，也不读类型策略。向导里勾的和“极速”实际覆盖的不是一套，界面上没有任何说明。
6. **入口与文档漂移。** 我在代码里只确认了主窗口搜索行的一个“扫描范围与收录…”入口；托盘菜单、空结果页是否有入口需实机核对。`SCAN_SETUP.md` 写“发现的整盘需显式点击发现并保持不勾选”，代码实际是自动探测并提供“勾选所有磁盘”按钮；`WINDOWS_USER_GUIDE.md` 写“不是 MFT/USN 索引器”，路线图却写 P2、P3（常驻与服务）已完成。

合起来解释了你的体验：**不是功能缺失，而是功能在流程里不可发现、不可恢复、与实际行为不一致。**

### 3.2 引擎与性能

**两套索引并存，执行语义不共享。** 主路径是 SQLite `files` 表（每行 20 多列，含 `name_fold`、`path_fold`、`parent_fold`），名字子串用 `instr()` 全表扫描；另一条是内存字节带（`compact_index.py`、`live_index.py`），用 `bytes.find` 线性扫描。查询语言（`query.py`，近 3000 行）被编译成带自定义函数（`LS_TEXT`、`LS_REGEXP`）的 SQL，内存引擎要把同一语义再实现一遍，你们路线图 P1 也承认“必须逐条对拍”。

**基准（我的沙箱，Python 3.12，100 万个合成文件名，取最优 5 次）：**

| 查询 | SQLite `instr`（现主路径） | 字节带 `find`（快索引路径） |
| --- | --- | --- |
| 常见词，命中约 10 万，取前 100 | 1.1 ms | 0.03 ms |
| 稀有词或未命中 | 57.6 ms | 14.9 ms |
| 复合词 `budget_final`，命中 2536，取前 100 | 6.3 ms | 0.34 ms |
| 名字带体量 | — | 20 MB |

线性外推到 270 万条，未命中约 150 ms 与 40 ms（外推，未实测）。含路径、多词、排序、属性过滤后只会更慢。两者都是线性扫描，最坏情况随索引线性增长。对照 plocate：作者页面的示例是 2700 万个文件、几毫秒找到 2 个，用的是三元组倒排，数据库 466 MB（mlocate 为 1.1 GB）。**结论：扫描式引擎在百万条内够用，到三百万条以上“未命中”就越过一帧，而打错一个字恰恰是最常见的未命中。**

**首扫差距**（你们文档的实测）：`C:\` 目录枚举约 450 项/秒（`auto_index.py` 注释）到 1430 项/秒（RESEARCH 文档）；MFT 路线 C: 约 264 万条、采集 9.11 秒，D: 约 56 万条、合计 2.79 秒，量级差约 140 倍。默认安装免提权，所以**默认走的是慢路径**，这是“装完要等很久才能搜”的第二个原因（第一个是范围不可选）。

**内存**：快索引在 C 盘全量为 121–142 MB（路线图）。Python 解释器加 PyQt5/Qt 的常驻基线我没有实测（通常是数十 MB 起），必须在 Windows 上测。网上有用户称 Listary 占 230 MB，那只是零散评论，不作依据。

**排序与拼音**：RRF 融合与终排已存在（30 条自建回归集 NDCG 0.957），但 Smith-Waterman 模糊匹配未做（RESEARCH §8 自述）；拼音只覆盖 GB2312 一级汉字的声母首字母，不支持全拼、多音字、模糊音，而 Listary 公开更新日志里已有全拼与模糊全拼。

**代码体量**：`gui.py` 4128 行，`query.py` 2997 行，`index.py` 1766 行，`duplicate_unicode.py` 4080 行（生成的映射表）。**依赖**：Qt 5.15.2 与 PCRE 8.45 均已停止维护（文档自述），PyQt5 为 GPLv3。

### 3.3 与 Listary 的体验差距

我在源码中检索了文件对话框、资源管理器、UI 自动化、窗口事件钩子等关键词，**没有发现 Quick Switch 或文件对话框集成**；没有应用启动器与开始菜单索引；没有命令、网页关键字或插件体系；没有对外的 API（ETP 客户端已作为墓碑移除，也没有 MCP、HTTP、IPC 接口）。双 Ctrl 快搜有，但未见“全屏游戏或应用自动停用”这类容错（Listary 6.3.0.51 更新日志已有）。

### 3.4 工程与合规

- **文档互相矛盾**：路线图写 P0–P7 全部“已完成”，VALIDATION 写候选包“尚未在本机交互验收、Windows 10 终验、UOS 验收均未完成”，且自述 41 模块里 21 项失败或被阻断；RESEARCH 文档写“没有实现 P1–P4 任何一项”，路线图却写 P1、P4 已完成。
- **测试**：我在 Linux 上跑了 8 个测试模块，5 个通过（其中 1 个全部跳过）；`test_compact_index` 1 个失败、`test_live_index` 2 个失败、`test_pinyin` 1 个错误。前两者明显是反斜杠与 `os.sep` 混用（期望 `V:\src\...` 得到 `V:\V:\\src\...`），说明核心路径拼接没有统一抽象。`pyproject.toml` 还忽略了 8 个 UI 测试，也没有 CI。
- **来源与许可**：见 §9。

## 5. 目标架构与关键技术选型

### 5.1 拆分原则

把“必须永远在线”的部分（索引、监听、查询）压到最小，把“可按需唤醒或重启”的部分（UI、内容抽取、OCR、语义）拆成独立进程。

```
xs-core（Rust，常驻，无 UI，目标 ≤ 40 MB）
  ├ VolumeProvider：NTFS/ReFS（MFT+USN）｜其他（目录枚举+变更通知）
  ├ 名字索引：名字带 + 倒排 + delta 段，mmap 快照
  ├ 查询执行器 + 排序管线 + 拼音/模糊
  └ 接口：命名管道（ACL）｜CLI｜MCP
xs-ui（可退出）：快搜窗口 / 工作台 / 托盘
xs-worker（按需）：内容抽取、OCR、嵌入（Python+ONNX 或 Rust）
```

### 5.2 三个方案

|  | A 渐进优化 | B 混合（推荐） | C 全部重写 |
| --- | --- | --- | --- |
| 做法 | 保留 Python/PyQt，优化 SQLite 与字节带 | Rust 核心；先保留 PyQt UI 通过 IPC 调用，之后再换 UI | 一次重写全部 |
| 周期 | 短 | 中 | 长，长期无可交付物 |
| 内存与延迟上限 | 受限于 Python | 核心达到 Everything 量级 | 同 B |
| 主要风险 | 天花板低 | 双语言工程与 IPC 边界 | 功能回归、士气 |

推荐 B。理由是第一性原理：常驻部分越小越稳越省，UI 是可唤醒、可重启的外壳。落地方式是先把现有测试里的**语法、排序、收录策略**转写成与语言无关的黄金用例（JSON），新旧引擎都必须跑通，再逐项切换，并保留回退开关（沿用你们“可见行为不许变差”的纪律）。

### 5.3 核心技术选型（每项带依据与验证方式）

1. **名字带 + 倒排索引。** 依据是 plocate 的三字节倒排与块压缩。西文用三元组；中文常见词只有 1–2 字，建议 CJK 用字符级 unigram 加 bigram；少于两个字符走前缀与首字母表加带扫描。这是我的设计推断，阶段 2 先做 PoC（300 万条合成加真实语料）量内存与延迟再定。
2. **增量与持久化。** USN 记录写入 delta 段，后台合并（LSM 思路），取代现在“墓碑 ≥ 5% 且 ≥ 5000 就整体重建”。保存 journal id 与下一个 USN，重启只重放差量，journal 被重建才全量。快照双缓冲加校验，并周期 checkpoint（Everything 官方说明数据库在退出时才落盘，异常退出可能丢失，这是可超越点）。
3. **排序管线：召回、特征、打分、解释。** 特征包括匹配类型（精确、前缀、词边界、子串、模糊、拼音）、位置、路径深度、新鲜度、frecency、类型偏好、同目录共访问、查询选择性（冷启动）。模糊匹配采用 Smith-Waterman 加仿射 gap（fzf、nucleo 同系，nucleo 的打分与 fzf 一致且在 helix 中经过大量实际使用；你们 RESEARCH 已整理常数）。先手调权重加离线评测集，积累本地打开日志后再做轻量线性或逻辑回归重排，数据永不出本机。
4. **拼音。** 全拼、简拼、混拼、模糊音（zh/z、sh/s、ch/c、n/l、an/ang 等），可选双拼。词典以 Unicode Unihan 的 kMandarin 字段为底自行生成（含多音字候选），不使用任何商业软件的数据文件；用 NFA 匹配而不是展开所有组合。
5. **内容与语义。** 一次抽取，词法与语义共用。词法用 BM25（Tantivy 或 SQLite FTS5，取决于 PoC 的内存与体积），CJK 用 bigram 或词典分词。语义分两档：低功耗档用静态嵌入（Model2Vec 一类，作者称可比原模型小 15 倍、快数百倍、约 30 MB，中文效果必须自测）；增强档沿用现有 BGE + ONNX。向量量化到 int8，十万级以内暴力扫描，超过再引入 HNSW（同意你们 RESEARCH §4 的判断）；融合沿用 RRF。
6. **OCR。** 保持 PP-OCR ONNX 路线；评测 Windows 自带 OCR 作为“零体积”选项；全部按需、低优先级、可暂停。
7. **智能排除。** 默认排除系统噪声与开发缓存（`WinSxS`、回收站、`node_modules`、`.git` 对象、浏览器缓存等），规则可见可改；可选借鉴 fd、ripgrep 的忽略文件规则。

### 5.4 权限与分发模型

三档并存，**永不静默降级**（沿用你们 P3 的原则）：

- **极速**：安装期一次管理员授权，注册只读 MFT/USN 的轻量服务，管道仅限当前用户。
- **按需提权**：不装服务，启动时 UAC 一次，用于一次性 MFT 快扫。
- **标准**：免提权，目录枚举加变更通知加低频校准扫描。

安装器、首次向导和设置页都要明确说明三档差别和代价。

## 6. 用户引导重做（阶段 1 的核心）

### 6.1 设计原则

一屏一个决定；默认值就是好答案；每个选项都说明代价；先能用，再完善；任何时候都能回来改。

### 6.2 关键设计决定：把“文件名层”和“内容层”分开设范围

这是回应你“选磁盘、选文件类型”需求的核心。

- **文件名层**（名字、路径、大小、时间）：成本很低（MFT 路径下 300 万条只要几秒、内存百兆级）。所以**默认覆盖所有固定本地卷**，类型默认“全部”，用智能排除挡掉噪声。用户可以按卷取消，也可以按类型收窄。按类型收窄的主要收益是结果更干净，省内存是次要的（Everything 官方也是把大小、日期等列为可选项来省内存）。
- **内容层**（正文、OCR、语义）：成本很高（CPU、磁盘、电池、缓存体积）。所以**默认关闭**，按目录、按类型单独授权，并在开关旁显示预估代价。
- **免提权的标准模式**：全盘目录枚举很慢（约千项/秒），所以默认“先索引常用目录，后台低优先级逐步扩到其他卷”，并显示覆盖进度，而不是让用户等全盘扫完。

这与你们现有“整盘不默认勾选、避免误触发全盘扫描”的原则不冲突：那条原则针对的是慢路径；MFT 路径下全盘文件名索引本来就便宜。

### 6.3 首次运行流程（目标 ≤ 60 秒、≤ 3 次点击）

| 步骤 | 用户看到什么 | 默认 | 要点 |
| --- | --- | --- | --- |
| 1 欢迎 | 一句话价值，两个按钮：“推荐设置（一键）”“自定义” | 推荐 | 点推荐直接跳到第 6 步 |
| 2 速度模式 | 检测到 NTFS 且可提权时，两张卡片：“极速（需一次授权，全盘文件名几秒就绪）”“标准（免授权，先索引常用目录）”；不可用时只显示标准并说明原因 | 极速（若可用） | 讲清楚授权做什么、不做什么；拒绝 UAC 不报错，自动进入标准 |
| 3 磁盘与目录 | 每个卷一张卡片：盘符、卷标、容量与已用、文件系统、预估条目数、预估耗时、能否极速；可添加或移除目录 | 极速模式：所有固定本地卷；标准模式：桌面、文档、下载 | 可移动盘、网络盘默认不选并说明原因 |
| 4 文件类型 | 场景卡片：办公与文档、图片与设计、音视频、代码与项目、压缩包与安装包、全部（含无后缀）；一个“智能排除系统噪声”开关；自定义后缀折叠到“高级” | 文件名层“全部” | 卡片上显示示例后缀，而不是让用户读后缀清单 |
| 5 内容检索（可选） | 正文、OCR、语义三个独立开关，旁边显示“约 N 个文档、后台约 M 分钟、占用约 K MB”，扫描到文档数后实时更新 | 全关 | 推荐设置下不弹这一页；常用目录扫完后用一条不打扰的提示问“发现 N 个文档，要开启正文搜索吗？” |
| 6 完成 | “现在就可以搜索”，三个示例查询（如 `*.pdf`、`xssj`、`ext:docx 报告`），提示“双击 Ctrl 随时呼出”；后台继续索引，显示“已可搜 N 项，覆盖 X/Y 卷” | — | 进度只显示可核验的数字。MFT 模式下总条目数在扫描前已知，可以给真实百分比；目录枚举模式沿用你们“不编造百分比”的做法 |

### 6.4 可发现与可恢复

- “稍后设置”不再等于“已完成”：`setup_wizard_completed` 改成三态（未开始 / 已跳过 / 已完成）。跳过后主窗口顶部出现一条细提示“还没选择搜索范围，当前仅索引常用目录”，最多提醒 3 次，之后只保留入口。
- 范围与类型入口放在这些位置：主窗口、托盘菜单、设置页、**空结果页**（“没找到？这个位置可能没被索引，点此添加”）、结果状态栏（“已索引 2 个卷 · 内容检索：关”）。
- 老用户升级：一次性、可关闭的轻提示，介绍新的范围页；不强制弹窗，不改变既有范围。
- 重新进入向导永远可用（保留 `--setup-wizard`，并在设置里加按钮）。单个卷、单个目录的设置可以就地修改（右键卷卡片）。

### 6.5 安装器（Inno Setup）

安装器只管安装，不做扫描。保留免提权默认；新增一个可选任务“安装极速服务（需要管理员）”，用一句话说清代价；结束页默认勾选“启动并开始设置”。范围选择放在应用首次运行，因为安装器无法可靠枚举和预估，也需要和应用共用同一套设置与迁移逻辑。

## 9. 合规与来源治理（先于一切发布）

我不是律师。下面是工程侧能做的风险收敛，正式发布前请请知识产权律师审阅。

**我在源码与文档里发现的事实**

1. 根目录 `LICENSE` 注明“Everything 原始资源、恢复伪代码、REA 证据”各自保留其许可；`AGENTS.md` 提到 `recovery/` 存放恢复证据与原始归档。
2. `duplicate_unicode.py` 的头注释说明，其 4062 条映射是用原版可执行文件逐对探测得到的。
3. `query.py` 的 `_ORIGINAL_KEYWORDS` 来源标注为“早期解码词表”，早期提取证据没有恢复。
4. 正文模块 `content_*` 借鉴了 Gety 0.9.0 的“独立实现”研究文件；THIRD\_PARTY.md 明说输入归档没有统一 LICENSE，不能宣称取得原厂许可。
5. 根目录 MIT 与发行包里的 GPLv3 PyQt5 并存；Qt 5.15.2、PCRE 8.45 已停止维护。

**建议**

1. **来源台账**：每个模块标注来源类别（自有原创 / 公开规范 / 第三方开源库 / 受限来源）。受限来源清零是发布门槛。
2. **清洁室**：对 Everything 的兼容限定在其公开文档化的搜索语法与可黑盒观察的行为上。一人写行为规格（只引用公开文档），另一人实现，实现者不接触恢复材料。Everything 的许可文本公开但源码不公开，对其二进制做反汇编或恢复伪代码是否被允许，取决于许可条款和所在法域，需要律师确认。
3. **替换受限数据**：`duplicate_unicode.py` 改用 Unicode 标准的 CaseFolding 与规范化数据；`_ORIGINAL_KEYWORDS` 改由公开文档中的语法列表重建；`content_*` 中借鉴 Gety 的部分重写，或取得书面授权。
4. **许可策略二选一**：(a) 整体采用 GPLv3，并保持源码对应分发；(b) 换用 LGPL 的 Qt 绑定（如 PySide6），或在新 UI 栈上重写，让自有代码保持宽松许可。新核心用 Rust，依赖以 MIT 或 Apache-2.0 为主，nucleo、plocate 等逐项核对。
5. **品牌与话术**：不暗示与 Everything、Listary、Gety 有关联；对比数据只用自己同机实测并注明版本。
6. **依赖安全**：升级到仍在维护的 Qt，用 PCRE2 或 Rust 的 regex 替代 PCRE 8.45；上线前做依赖 CVE 扫描。

## 10. 需要你拍板的问题

1. **是否公开或商业发布？** 这决定 §9 的力度。仅自用可以压缩；要公开，§9 是阶段 0 的硬门槛。
2. **平台范围**：只做 Windows，还是同时保留统信 UOS 与 Linux？Linux 没有 MFT，要另走 fanotify、inotify 加目录枚举，VolumeProvider 与测试矩阵会翻倍。我建议先 Windows，保持 Linux 可编译。
3. **是否接受一次管理员授权？** 接受，才能默认做到全盘秒级；不接受，就主打“常用目录先搜，后台扩展”。
4. **UI 技术栈**：短期保留 PyQt5（经 IPC），长期在 Qt 6/C++、Tauri/WebView2、Slint 等里选。我倾向体积与内存优先的原生方案；要不要 WebView2，取决于你对“占用内存更少”的优先级。
5. **人力与节奏**：§7 的周期按 2 名全职工程师估算。如果只有你一人加 AI 协作，请把阶段 2–4 拉长一倍，并先砍掉阶段 3 的系统集成。
6. **是否允许联网更新？** 与“零联网”承诺冲突，建议默认关闭、手动检查。
