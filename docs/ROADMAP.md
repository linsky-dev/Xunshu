## P0 协议补齐与文档纠错

**问题**：`docs/FAST_PATH_INTEGRATION_PLAN.md` 里"按路径取回带身份的行"是错的。快搜结果协议禁止结果行携带 `device/inode` 等访问凭据：

```
_RESULT_KEYS = {schema, version, request, complete, candidate_count, matched_total, rows, elapsed_ms}
_ROW_KEYS    = _SELECTION_KEYS | {match_reason, match_kinds, rank, pinned, recent}
```

身份核验只发生在打开时（`guarded_quick_resolve`）。

**交付物**
1. 更正设计文档：候选流 = 快索引给 `path` → **投影成协议行** → 打开时再核验身份
2. `linsearch/quick_row.py`：`project_to_quick_row(row, *, reason, kinds, rank, pinned, recent)` 纯函数
3. 词表落地：从 `quick_selection` / `match_reason` 取受控取值，不自行发明

**验收**
- 投影函数单测覆盖：字段集合恰好等于 `_ROW_KEYS`、缺字段/多字段都抛错
- 用合成库跑 `validate_quick_result` 通过

**风险**：`match_reason` 若存在枚举约束，取值必须来自既有定义；这一点必须先读代码确认，不得猜。

## P1 快索引接入快搜

**目标**：搜到结果的第一屏由内存索引产出，SQLite 退为解析与兜底。

**做法**
```
GUI: fast.search(term, limit) → paths[]        （纯内存，<1 ms，无磁盘 IO）
  ↓ 投影成协议行（P0）
  ↓ validate_quick_result（既有闸门不动）
_paint
```

**关键约束**
- 不在 GUI 进程读 SQLite（磁盘可能卡住，破坏可终止性）
- 不把索引序列化传子进程（25–120 MB 拷贝比查询本身贵几个数量级）
- 回退开关：`SearchBackend.ready()` 为假、投影抛错、paths 为空 → 一律走原 `guarded_quick_search`

**交付物**
1. `QuickPanel` 持有 `SearchBackend`（默认 None，行为与现在完全一致）
2. `_dispatch` 分支 + 回退
3. 6 项集成测试：顺序、空候选、路径已删、超时、取消、身份缺失

**验收**
- 离屏验证：快索引命中 → 双击打开 → 身份核验通过
- 故意让 `fast_paths` 抛错：界面回到老路径且结果正确，不出现空白
- 同一查询在新旧路径下结果集**逐条一致**（顺序可不同）

**风险**：高。这是唯一会改变用户可见行为的阶段，必须逐条对拍。

## P2 索引常驻与增量

**目标**：打开软件即可搜，不用等首扫；文件变动 5 秒内可见。

**做法**
1. 启动后台线程 `create_for_volume(系统盘)`：MFT 全量 → 内存索引（实测 3.8 s / 55.9 万条）
2. USN 轮询线程：`read_journal` → `apply_usn`（实测 16 µs/条）
3. 墓碑策略：`≥5000 且 ≥5%` 触发整体重建（重建走 MFT，约 4–5 s）
4. 索引就绪前，界面继续用 SQLite，不阻塞

**验收**
- 冷启动到"快索引可用"≤ 6 s（C 盘 264 万条推算约 20 s，需实测）
- 外部改名/新建/删除，5 秒内在结果中体现
- 墓碑触发重建后，`items` 与实际文件数误差 ≤ 0.1%

**风险**：内存 121–142 MB（C 盘全量）；32 位或低配机器需评估；需提供"关闭快索引"开关。

## P3 系统服务

**目标**：索引常驻，进程重启不用重建。

**内容**
- SCM 注册（`LocalSystem`）、命名管道协议、管道 ACL（限当前用户 + Administrators）
- 安装器提权（**这会改变安装模型**：从 HKCU 免提权 → 需要管理员）
- 无服务时回退到进程内建索引（P2）

**验收**
- 服务启停、异常退出自恢复、卸载无残留（含注册表与管道）
- 普通用户身份下客户端可读、不可写管道
- 未提权安装时：功能完整，只是没有常驻（明确告知，不静默降级）

**风险**：高。权限模型变更、双平台分叉（Linux 侧无对等实现）、卸载残留。

## P4 检索质量

**目标**：一个搜索框出结果，按相关性排，能看到命中原因。

**内容**
1. **RRF 融合**：`Σ w/(k+rank)` 合并文件名/正文/语义三路（模块已完成，14 项测试）
2. **终排**：精确名（含去扩展名）、前缀、路径深度、指数新鲜度、frecency（模块已完成）
3. **片段**：正文命中片段（已接选中行）；扩展为结果列或行内高亮
4. **冷启动信号**：查询结果数作为排序特征（TOIS 2008 的 query selectiveness）

**验收**
- 构造 30 条固定查询的回归集，融合前后 NDCG 不下降
- 三路召回都为空时才返回空，单路命中必须出现

**风险**：中。排序语义变更需保留旧排序开关。

## 执行顺序与理由

```
P0 → P1 → P2 → P3
      ↘ P4（可与 P2 并行）
P5、P6、P7 独立，按资源穿插
```

- **P0 先做**：不先把协议字段搞清楚，P1 一定返工（已经返工过一次）。
- **P1 在 P2 前**：先证明"接得上且不退化"，再谈常驻；否则常驻只是把问题放大。
- **P3 最后**：服务只解决"谁常驻"，不解决"索引怎么建"。P1/P2 没过就做服务，等于给慢路径加壳。
- **P4 可并行**：排序模块已独立且有测试，不阻塞。
